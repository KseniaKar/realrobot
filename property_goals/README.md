# Property Goals

Исторические данные по лотам `investmoscow`, которые реально были куплены, и попытка восстановить их пост-покупочное использование.

## Что лежит в папке

- `app.py` — Streamlit-приложение.
- `requirements.txt` — зависимости для деплоя.
- `investmoscow_sold_2022_2026.csv` — исходный экспорт купленных лотов.
- `investmoscow_sold_2022_2026_clean.csv` — очищенный CSV без лишних технических полей.
- `investmoscow_sold_2022_2026_clean.with_norm.csv` — тот же CSV с нормализованным адресом `address_norm`.
- `investmoscow_sold_2022_2026_enriched.csv` — лоты с первым matching по использованию.
- `investmoscow_sold_2022_2026_enriched_geo.csv` — финальный файл после всех этапов очистки и восстановления.
- `moscow/` — снапшоты справочника организаций Москвы по датам.
- `matches/` — промежуточные и итоговые результаты матчинга.

## Как отбирались лоты

В выборку попадают только реально купленные лоты:

- есть `итоговая_цена_руб`
- нет признака `Отказ победителя`

Срез по годам:

- `2022`: 737
- `2023`: 971
- `2024`: 870
- `2025`: 1065
- `2026`: 225

Всего: `3868` лотов.

## Логика матчинга

Цель — не найти покупателя по протоколу, а понять, что появилось на объекте после покупки:

- вероятное название компании
- вероятная категория использования

### Шаг 1. Нормализация адресов

Для лотов и для снапшотов `moscow` были нормализованы адреса:

- убраны `г. Москва`, округа и служебные префиксы
- приведены к единому виду `улица / дом / корпус / строение`
- отброшены этажи, помещения, подвалы и прочие внутренние хвосты

Результат:

- `investmoscow_sold_2022_2026_clean.with_norm.csv`
- `moscow/*.with_norm.csv`

### Шаг 2. Exact match по адресу

Для каждого лота строился первый строгий матч:

- по `address_norm`
- по ближайшему снапшоту после даты покупки

Промежуточные файлы:

- `matches/property_usage_best_match_exact.csv`
- `matches/property_usage_all_matches_exact.csv`

### Шаг 3. Before / after

Матчинг усиливается сравнением снапшотов:

- `before` — ближайший снапшот до покупки
- `after` — ближайший снапшот после покупки
- кандидаты — только компании, которые появились в `after`, но отсутствовали в `before`

Промежуточные файлы:

- `matches/property_usage_before_after_best.csv`
- `matches/property_usage_before_after_new_companies.csv`

### Шаг 4. High / medium

Из результата `before/after` выделены более пригодные кейсы:

- `high`
- `medium`

Промежуточные файлы:

- `matches/property_usage_before_after_best_high_medium.csv`
- `matches/property_usage_top_candidates_high_medium.csv`
- `matches/property_usage_likely_summary.csv`

### Шаг 5. Гео-проверка

Кандидаты проверяются по координатам:

- `0-30m`, `30-100m` — оставляем
- `100-250m` — понижаем до `low`
- `250m+` — исключаем

Файл проверки: `matches/property_usage_geo_verified.csv`

### Шаг 6. Временной фильтр + recent matching

Baseline matching: временное окно `180-365` дней после покупки. Защита от ложных совпадений с уже существовавшими организациями — по `match_id` и по схожести имени в радиусе `100 м`.

Для недавних продаж построен отдельный recent matching по снапшоту `2026-04`:

- окно: `0-180` дней до `2026-04-30`
- скрипты: `process_2026_04_snapshot.py` → `match_recent_2026_04.py` → `merge_recent_2026_04_matches.py`

### Шаг 7. Реvalidация — фильтр по типу бизнеса

Скрипт: `revalidate_matches.py`

Использует требования из `../retailstreets_parser/data/retailstreets_requirements.csv` как критерий правдоподобности. Для каждого кандидата проверяется:

1. **Тип бизнеса** — удаляются кандидаты, которые не могут быть самостоятельными арендаторами:
   - устройства (зарядные станции, постаматы, водоматы, кофейные автоматы)
   - госслужбы (справочные, диспетчерские ЖКУ, правоохранительные органы)
   - жилые комплексы (`Новостройки`)
   - общественные организации

2. **Соответствие площади** — для категорий с известными требованиями (алкомаркеты, ПВЗ, супермаркеты и др.) проверяется, что площадь лота не выходит за допустимый диапазон (с 4x tolerance).

Результат реvalidации (от 185 матчей):

- `37` очищены полностью (все кандидаты невалидны)
- `18` улучшены (плохой кандидат убран, остался реальный арендатор)
- `130` без изменений

Главный паттерн ложных матчей: **Центры информирования по переселению** (программа реновации Москвы) — 27 лотов подряд в одном районе.

Отчёт: `matches/revalidation_report.csv`

### Шаг 8. Восстановление лотов 2022–2024

Скрипт: `recover_lost_matches.py`

**Проблема:** снапшоты справочника покрывают `2020-04–2021-10`, затем сразу `2025-09`. Для лотов 2022–2023 ближайший `after`-снапшот — `2025-09` (~1000 дней), что выходит за окно `180-365` дней.

**Решение:** для лотов без матча, у которых есть гео-кандидаты в `geo_verified.csv` с `after_days > 180`, принимается первый доступный `after`-снапшот независимо от количества дней. Те же реvalidation-фильтры (тип бизнеса + площадь) применяются и здесь. Матч `high` понижается до `medium` при `after_days > 365`.

Результат: `+223` новых матча для лотов 2022–2024.

Лейбл в данных: `match_time_window = "first_after_snapshot_2025-09"`.

Отчёт: `matches/recovered_matches_report.csv`

## Что использует приложение

`app.py` читает данные в таком порядке:

1. `investmoscow_sold_2022_2026_enriched_geo.csv`
2. `investmoscow_sold_2022_2026_enriched.csv`
3. `investmoscow_sold_2022_2026_clean.csv`

## Что показывает приложение

- карта купленных лотов (фильтрация по Usage match, возможность показать все лоты)
- фильтры по форме, году, округу, этажу, цене, площади и `Usage match`
- метрики по выборке
- scatter `участники ↔ превышение`
- таблица с `Likely company`, `Likely usage`, `Usage match`, `Match source`

## Ограничения

- В справочнике `moscow` нет кадастрового номера — проверка по адресу, времени и координатам.
- На одном адресе может быть несколько компаний и несколько помещений.
- `likely_company` и `likely_usage` — вероятностная реконструкция, не юридически точное доказательство.
- Для лотов 2022–2023 окно неопределённости ~4 года (нет снапшотов за 2022–2024).
